## 0. 검증자에게 요청하는 사항
1. 기술 스택 선택(특히 STT)이 제약조건(7주·1인·예산·개인정보)에 맞는가
2. 개인정보 처리 설계에 법적·운영상 빈틈이 있는가 (외부 API로 음성 전송 문제 포함)

5. 아래 "미확인·가정" 항목 중 틀린 것이 있는가

## 1. 서비스 개요
- **이름:** 돌봄이음
- **한 줄 정의:** 돌봄인력이 어르신 방문 직후 30초 구술하면, AI가 ① 규격 돌봄기록 초안 ② 기관 간 인수인계 브리핑 ③ 이상징후 표시·알림 초안을 만들어 주는 기록·연계 보조 서비스
- **사용자:** 광주 통합돌봄 현장 돌봄인력(약 1,200명), 동 행정복지센터 담당자(96개 동), 서비스 제공기관(70개)
- **원칙:** AI 결과는 모두 "초안"이다. 사람이 확인·수정 후 사용하며, AI는 위험을 판정하지 않고 "확인 필요 신호"만 제시한다. 기존 시스템을 대체하지 않고 복사·붙여넣기용 초안을 제공하는 보조 도구다.

## 3. 핵심 기능 명세

### 기능 ① 음성 → 규격 돌봄기록 초안 (최소 완성 요건, 최우선)
- 입력: 돌봄인력 본인의 구술(어르신 음성 아님) 약 30초, 또는 텍스트 직접 입력
- 처리: STT → LLM이 구조화 JSON으로 변환
- 출력: 「2026년 노인맞춤돌봄서비스 사업안내」의 기록 항목에 맞춘 초안 + "복사" 버튼
- 사용자가 수정 후 저장 → 수정 여부와 수정량을 기록(수용률 측정용)

### 기능 ③ 이상징후 플래그 + 알림 초안 (4주차)
- 탐지 대상 5종: 약 미복용, 식사량 감소, 낙상, 정서적 위축, 방문 거부
- 출력: 플래그 목록(근거 문장 인용 포함), 수준(관찰/주의), 동 담당자·연계기관용 알림 문안 초안
- 실제 발송 기능은 MVP에서 제외: 문안 복사 → 기존 채널(문자·메신저)로 사람이 전송
- 대시보드: 플래그가 있는 대상자를 상단 정렬

### 기능 ② 기관 간 인수인계 브리핑 (5주차)
- 입력: 대상자 식별번호 + 기간(기본 최근 2주)
- 처리: 여러 기관·담당자의 기록을 시간순으로 모아 LLM이 요약
- 출력: "지난 2주간 이 어르신에게 무슨 일이 있었는가" 한 장 요약 + 미해결 이상징후

## 4. 기술 스택
| 영역 | 선택 | 근거 |
|---|---|---|
| 프론트 | Next.js(App Router) + TypeScript + Tailwind CSS + shadcn/ui, PWA | 계획서 명시, 설치 없는 모바일 웹 |
| 백엔드 | Next.js Route Handlers / Server Actions (별도 서버 없음) | 1인·7주, 코드베이스 1개, API 키 서버 보관 |
| DB·인증 | Supabase (Postgres + Auth + RLS) | 기관·담당자별 접근통제를 RLS로 처리, 무료 티어 |
| STT 메인 | Groq API `whisper-large-v3-turbo` (무료 티어) | 무료 중 정확도·속도 최상위 (30초 음성 약 1초) |
| STT 보조 | 브라우저 Web Speech API | 말하는 중 실시간 글자 표시, Groq 장애 시 대체 |
| STT 최종 대체 | 텍스트 직접 입력 | 계획서의 극복방안과 일치 |
| LLM | Claude API `claude-sonnet-5-5`, JSON 스키마 구조화 출력 | 기록 서식·플래그 형식을 스키마로 고정 |
| 호스팅 | Vercel (Hobby로 시작) + Supabase 서울 리전 | git push 배포, HTTPS 기본(마이크 권한 필수) |
| 도메인 | `dolbomieum.kr` — 가비아 네임서버를 Cloudflare로 변경 → Cloudflare DNS에서 Vercel로 연결, 프록시 끔(DNS only) | Vercel이 SSL 자동 발급·갱신 |

### 정식 운영 시 교체 경로
- STT: 같은 인터페이스 뒤에서 OpenAI `gpt-4o-transcribe` 또는 국내 STT(네이버 CLOVA Speech, 리턴제로)로 교체 → 국내 서버 처리로 기관 설득에 유리
- 호스팅: Vercel Hobby는 비상업용 조건 → 정식 운영 시 Pro 또는 Cloudflare Workers(OpenNext) 검토

## 5. 처리 흐름

```
[휴대폰 브라우저]
 ├─ 대상자 식별번호 선택
 ├─ 녹음 (MediaRecorder, opus/webm, 모노) ── 동시에 → Web Speech API로 실시간 글자 표시
 └─ 녹음 종료 → 음성 업로드 (실측: 크롬 기본 음질 30초 ≈ 410KB, 32kbps로 낮추면 ≈ 120KB)
        ↓
[POST /api/transcribe]
 ├─ Groq Whisper 호출 (language="ko", prompt=돌봄 용어 힌트)
 ├─ 실패 시 클라이언트의 Web Speech 결과 사용
 └─ 음성은 메모리에서만 처리 후 폐기 (파일·스토리지 저장 안 함, 로그에도 안 남김)
        ↓
[POST /api/draft]  (스트리밍 응답)
 ├─ 성명·주소·전화번호 패턴 마스킹 (서버측 정규식, LLM 호출 전)
 ├─ Claude 호출 → 기록초안 JSON + 이상징후 플래그 + 알림 초안
 └─ 화면에 스트리밍 출력
        ↓
[화면] 확인·수정 → 저장 (visit_records)
```

- 목표 체감 지연: 녹음 종료 후 초안 첫 글자 2~3초, 전체 3~5초 (실측 아님, 추정)
- 속도 장치: opus 압축 업로드, 실시간 미리보기, LLM 스트리밍, 돌봄 용어 힌트로 재처리 감소

## 6. 데이터 모델 (Supabase Postgres)

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `agencies` | id, name, type(동센터/수행기관/복지관) | |
| `workers` | id(auth.users), agency_id, role(worker/manager), display_name | 성명 대신 표시명 허용 |
| `clients` | id, code(식별번호), agency_ids[], created_at | 성명·주소·연락처 컬럼 없음 |
| `visit_records` | id, client_id, worker_id, agency_id, visited_at, transcript_text, draft_json, final_json, edited(bool), edit_ratio, input_mode(voice/text), stt_engine, duration_ms(녹음~저장 소요), created_at | 수용률·작성시간 측정 |
| `flags` | id, record_id, client_id, type(5종), level(관찰/주의), evidence_quote, status(미확인/확인/조치), resolved_by | |
| `alert_drafts` | id, flag_id, target(동담당자/연계기관), body, copied_at | 실제 발송은 사람이 |
| `briefings` | id, client_id, period_from, period_to, body, created_by | 생성 기록 보관 여부는 검토 필요 |

- RLS: worker는 본인 기관이 연계된 대상자의 기록만 조회. manager는 기관 전체 조회.
- 성과지표 산출: 수용률 = 수정 없이 또는 경미 수정으로 저장된 비율(edit_ratio 기준 임계값 정의 필요), 작성시간 = duration_ms 평균 vs 사전조사 기존 작성시간

## 7. 화면 구성
참고 시안: `doc/design_ui.png` (발표자료 7번 슬라이드 가상연출도). 사용자별로 두 갈래로 나눈다.

### 7-1. 현장 돌봄인력용 — 모바일 중심 (시안에 없음, 신규 설계)
1. 로그인
2. 오늘의 방문: 오늘 방문할 대상자 목록
3. 기록하기: 대상자 선택 → 큰 녹음 버튼 → 실시간 글자 표시 → 기록 초안 → 수정 → [저장] [복사]
   - 같은 화면에 텍스트 직접 입력 전환 버튼
   - 초안 하단에 탐지된 이상징후 카드(근거 문장 포함) 표시
4. 내 기록: 최근 작성한 기록 목록, 다시 복사

### 7-2. 동 담당자·기관용 — PC 대시보드 (시안 기준)
- **레이아웃:** 왼쪽 남색 사이드바 + 본문
  - 사이드바 상단: 서비스명 "돌봄이음", 기관 선택
  - 업무 메뉴: 오늘의 방문 / 기록 작성 / 인수인계 브리핑 / 이상징후 현황(미확인 건수 배지)
  - 관리 메뉴: 대상자 목록 / 연계 기관 / 설정
  - 하단: 로그인 사용자(소속·담당) / 로그아웃
- **이상징후 현황 (메인)**
  - 상단 한 줄 요약: "오늘 N명 중 먼저 볼 M명", 기준 시각, 오늘 접수 기록 수
  - 요약 카드 4개(작은 추이 그래프 포함): 주의 필요 / 관찰 지속 / 특이사항 없음 / 이번 달 조기 발견
  - "먼저 확인할 어르신" 목록: 순위, 대상자 표시, 신호 요약 한 줄, 상태 배지(주의·관찰·해소), 관련 기관 수, [브리핑] 버튼
  - 정렬 기준: 위험 신호 개수 → 지속 기간 → 중복 관찰 기관 수
  - 기간 필터
- **알림 상세 (모바일에서도 동작)**
  - "확인이 필요해요" 헤더, 여러 신호가 같은 시기에 겹칠 때 경고 문구
  - 신호별 카드: 신호명, 지속 일수·신규 배지, 근거, 타 기관 관찰 여부
  - 연계 알림 문안 초안 + [수정] [복사]
- **인수인계 브리핑:** 대상자·기간 선택 → 한 장 요약 + 미해결 이상징후
- **대상자 목록 / 연계 기관:** 등록·조회(최소 기능)
- 모든 AI 결과 화면 하단에 원칙 문구: "AI는 판정하지 않고, 담당자에게 확인을 요청합니다"

### 7-3. 디자인 기준 (시안 기준)

## 8. 프롬프트 설계 방향
- 시스템 프롬프트에 노인맞춤돌봄 기록 항목 정의, 이상징후 5종 정의와 판단 기준, "판정하지 말 것·근거 문장을 인용할 것·추측 금지" 규칙 포함
- 출력은 JSON 스키마로 고정, 항목 누락 시 빈 값 허용(지어내지 않기)
- STT 오인식 보정은 문맥상 명확한 경우만, 보정한 부분은 표시

## 9. 개인정보·보안
- 음성: 서버 메모리 처리 후 폐기, 저장 없음
- 식별정보: DB 스키마에 성명·주소 컬럼 자체가 없음, LLM 호출 전 정규식 마스킹
- 외부 전송: 음성은 Groq(미국), 텍스트는 Anthropic(미국)으로 전송됨 → 실증 동의서에 명시 필요, 구술 시 성명 대신 식별번호로 말하도록 안내
- API 키는 서버 환경변수에만, 클라이언트 노출 금지
- 로그에 구술 텍스트 남기지 않기

## 9-1. 기기 호환성 (마이크 접근)
앱 설치 없이 브라우저 표준 API(`getUserMedia` + `MediaRecorder`)로 안드로이드·아이폰 모두 녹음 가능하다. 단, 브라우저 권한 요청은 우회할 수 없으므로 "한 번 허용하면 끝나도록" 설계한다. 아래 표는 알려진 브라우저 동작 기준이며, "실기기 확인" 표시가 있는 줄은 `/mic-test`로 실제 확인한 결과다.

| 환경 | 녹음 | 실시간 글자(Web Speech) | 주의 |
|---|---|---|---|
| 안드로이드 크롬 | **가능 (실기기 확인 2026-10-10: webm/opus, 7초 95.7KB, 재생 정상)** | **불가 (실기기 확인 2026-10-11: 단독·녹음과 동시 모두 인식된 글자 없음, 오류 없음. 녹음은 동시 사용 중에도 정상)** | 사이트별 허용이 유지됨 |
| 삼성 인터넷 | 가능 | 불안정 가능 | 실기기 테스트 필요 |
| 아이폰 사파리 (iOS 14.3+) | 가능 | 가능(간헐 끊김) | 방문마다 권한을 다시 물을 수 있음 |
| 아이폰 크롬·네이버앱 | 가능 | 앱마다 다름 | iOS는 모두 WebKit 엔진 |
| 카카오톡 등 인앱 브라우저 | 막히는 경우 많음 | 불가 | 외부 브라우저로 열기 유도 |

- **필수 조건:** HTTPS (`dolbomieum.kr` + Vercel SSL로 충족)

### 구현 대응
1. **녹음 포맷 자동 선택:** `MediaRecorder.isTypeSupported()`로 확인 → 안드로이드 `audio/webm;codecs=opus`, 아이폰 `audio/mp4`(AAC). Groq Whisper는 두 형식 모두 지원
2. **권한 사전 안내 화면:** 첫 사용 시 "녹음을 위해 마이크 허용이 필요합니다" 안내 후 권한 요청. 거부 시 기기별 설정 방법 표시(아이폰: 설정 → Safari → 마이크 → 허용, 안드로이드 크롬: 주소창 자물쇠 → 권한)
3. **인앱 브라우저 감지:** User-Agent로 카카오톡 등 인앱 브라우저를 감지해 "크롬/사파리로 열기" 안내 (안드로이드 카카오톡은 외부 브라우저 열기 링크 제공)
4. **실시간 글자는 선택 기능:** 일부 기기에서 녹음과 Web Speech 동시 사용 시 마이크 충돌 가능 → 녹음을 우선, 실시간 글자는 지원·정상 동작 기기에서만 활성화
5. **화면 꺼짐 방지:** 녹음 중 Screen Wake Lock API 사용(미지원 기기는 안내 문구)
6. **PWA 홈 화면 추가 안내:** 아이콘으로 바로 실행. 아이폰은 권한 재요청 가능성 있음
7. **최후 대체:** 마이크 불가 기기는 텍스트 직접 입력으로 기록 가능
8. **녹음 길이 제한:** 최대 2분 자동 종료(업로드 크기·비용 관리)

## 11. 예산 추정 (재료비 150만원 내)
- STT: Groq 무료 티어로 파일럿 규모 처리 가능할 것으로 예상(미확인)
- LLM: 기록 200~500건 + 브리핑 → 수만 원 수준 예상
- 호스팅·DB: Vercel Hobby, Supabase Free로 시작 → 0원
- 도메인: 연 1~3만원

## 12. 미확인·가정 (검증 필요)
1. Groq 무료 티어의 현재 한도, 데이터 보존·학습 정책, 모델명 — 오늘 기준으로 재확인하지 않음
2. Web Speech API의 iOS 사파리 한국어 동작 안정성
3. Vercel Hobby 플랜을 공모전 파일럿에 써도 되는지(비상업 조건 해석)
4. 외부(해외) API로 돌봄 관련 음성·텍스트를 보내는 것이 실증기관 보안 기준에 맞는지 — 국내 STT로 시작해야 할 수도 있음
5. 노인맞춤돌봄 기록 서식의 정확한 항목 — 사업안내 원문 분석 전
6. 체감 지연 3~5초는 추정치, 실측 필요
7. 수용률 "경미 수정"의 기준값
8. 기기별 마이크·Web Speech 동작(특히 삼성 인터넷, 아이폰 PWA, 카카오톡 인앱 브라우저) — 실기기 미검증

## 13. 검증 방법
- 실제 휴대폰(HTTPS 배포본)에서 30초 녹음 → 초안이 기록 항목대로 나오는지
- 샘플 구술 10~20건으로 이상징후 5종 탐지 정확도 수동 점검
- DB·로그·스토리지에 음성 파일과 성명이 남지 않는지 점검
- 녹음 종료~초안 표시 시간 실측
- 1주차 배포 직후 기기 호환성 테스트: 갤럭시(크롬·삼성 인터넷), 아이폰(사파리·홈 화면 PWA), 카카오톡 링크로 연 경우 → 녹음·업로드·STT까지 확인
- 사전 수요조사에 "사용 기종·브라우저" 문항 추가하여 파일럿 대상 기기 사전 파악
