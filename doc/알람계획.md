# 관리자 → 현장인력 웹푸시 알림 계획

> 2026-10-20 작성. 한 기관에서 받은 의뢰("관리자가 수동으로, 또는 긴급히 도움이 필요할 때 현장인력에게 자동 웹푸시 알림을 띄울 수 있는가")에 대한 검토와 구현 계획.

## 답변 요약
- **가능합니다.** 앱을 새로 만들지 않고 지금의 돌봄이음 웹 서비스에 기능을 더하면 됩니다.
  - 발송 비용은 없습니다. Vercel·Supabase로 보내며 문자 요금이 들지 않습니다.
- **긴급 상황을 맡기는 유일한 연락 수단으로는 쓰지 않습니다.**
  - 도착이 보장되지 않고, 무음 모드를 뚫고 울리게 할 수 없습니다.
  - 그래서 "확인 버튼 + 정해진 시간 안에 확인이 없으면 관리자가 전화로 이어받는" 구조로 만듭니다.
- **AI가 찾은 이상징후를 바로 자동 발송하지 않습니다.** 관리자가 확인한 뒤 보냅니다.
  - AI가 잘못 판단할 수 있고, 잘못된 긴급 알림이 쌓이면 현장인력이 알림을 꺼 버립니다.

## 현재 상태
- 이미 있는 것
  - 홈 화면에 추가하는 앱 설정: `web/src/app/manifest.ts`, `web/src/app/layout.tsx`
  - 홈 화면 추가 안내: `web/src/app/guide/page.tsx`
- 아직 없는 것: 서비스 워커, 알림 받을 기기 등록, 발송 기능, 알림 확인 기록
- 지금의 "알림 문안"(`alert_drafts`)은 반대 방향입니다.
  - 현장 기록을 바탕으로 동 담당자에게 보낼 글을 만들어 복사해 주는 기능이고, 실제 발송은 하지 않습니다.

## 기기별 지원
| 환경 | 웹푸시 | 비고 |
|---|---|---|
| 안드로이드 크롬·삼성 인터넷 | 됨 | 알림 허용 1회 필요. 알림 안의 버튼(수락/불가)도 됨 |
| 아이폰 사파리 | iOS 16.4 이상, **홈 화면에 추가한 뒤에만** 됨 | 알림 안의 버튼은 안 됨. 알림을 눌러 앱 화면에서 응답 |
| 카카오톡 등 앱 안의 브라우저 | 안 됨 | 크롬·사파리로 열도록 안내 |

## 한계 (기관에 미리 설명할 부분)
1. **도착이 보장되지 않습니다.** 보통 몇 초 안에 오지만, 전화기가 꺼져 있거나 절전·방해금지 모드이거나 사용자가 알림을 끄면 늦거나 오지 않습니다.
2. **무음 모드를 뚫고 울리게 할 수 없습니다.**
3. **보냈다는 것만으로는 읽었는지 알 수 없습니다.** 확인 버튼과 미확인 표시로 보완합니다.
4. **잠금 화면에 내용이 보입니다.**
   - 알림 본문에는 대상자 이름, 식별번호, 건강 정보를 넣지 않습니다. 예: "긴급 요청 1건이 있습니다".
   - 자세한 내용은 로그인한 뒤 앱 화면에서 봅니다.

## 시나리오

### 잘 맞는 경우
| No | 시나리오 | 누가 보내나 | 등급 |
|---|---|---|---|
| ① | **어르신 안부 확인 요청**: 안부전화를 받지 않거나 연락이 끊겼을 때, 담당자나 근처 인력에게 "방문 확인이 가능한가요?" 요청. 받은 사람이 [수락]/[불가]로 답함 | 관리자 (수동) | 긴급 |
| ② | **대체 방문 요청**: 담당 인력이 결근했을 때 같은 기관 인력들에게 동시에 보내고, 먼저 수락한 사람에게 배정 | 관리자 (수동) | 긴급 |
| ③ | **폭염·한파 등 재난 특보 때 일괄 안부 확인 지시** | 관리자 (수동, 동 단위) | 업무 요청 |
| ④ | **이상징후 후속 조치**: 다른 기관 기록에서 위험 신호가 나왔을 때 담당 인력에게 "다음 방문 때 약 복용 확인" 같은 요청 | 관리자가 신호를 확인한 뒤 발송 | 업무 요청 |
| ⑤ | **기록 누락 알림**: 방문 후 기록이 없으면 저녁에 자동으로 알림 | 자동 | 안내 |

### 맞지 않는 경우
- **생명이 걸린 응급 상황**: 낙상이나 의식 저하가 의심되면 119와 전화가 먼저입니다. 푸시는 그 뒤에 같이 알리는 보조 수단입니다.
- **반드시 받았는지 확인해야 하는 지시**: 푸시만으로는 안 되고, 확인이 없으면 전화나 문자로 이어지게 합니다.
- **자잘한 공지를 자주 보내는 용도**: 알림 피로가 쌓이면 정작 긴급 알림도 무시하게 됩니다.

## 알림 등급
| 등급 | 시나리오 | 확인 요구 | 미확인 처리 | 푸시 설정 |
|---|---|---|---|---|
| 긴급 | ①② | [수락]/[불가] | 10분 안에 아무도 수락하지 않으면 관리자 화면에 "전화 연락 필요" 표시 | Urgency `high`, TTL 1시간 |
| 업무 요청 | ③④ | [확인] | 당일 미확인 인원을 관리자 화면에 표시 | Urgency `normal`, TTL 1일 |
| 안내 | ⑤ | 없음 | 없음 | Urgency `low`, TTL 1일 |

- 미확인 시간 기준(10분)은 기관과 정합니다.
- "전화 연락 필요"는 별도 예약 작업 없이 관리자 화면을 열 때 계산해서 보여 줍니다. 화면은 주기적으로 새로 고칩니다.

## 설계

### 1. 기기 등록 (현장인력 쪽)
- `web/public/sw.js` (서비스 워커): `push` 이벤트에서 알림을 띄우고, `notificationclick` 이벤트에서 `/alerts/[id]` 화면을 엽니다.
- 설정 화면에 **"알림 받기" 버튼**을 둡니다.
  - 브라우저는 사용자가 버튼을 눌렀을 때만 알림 권한을 요청할 수 있습니다. 특히 아이폰이 그렇습니다.
  - 허용하면 구독 정보를 서버에 저장합니다.
- 아이폰에서 홈 화면 앱이 아니면 버튼 대신 "홈 화면에 추가한 뒤 켤 수 있습니다" 안내를 보여 줍니다. 기존 `lib/audio/environment.ts`의 standalone 판별을 재사용합니다.
- **"테스트 알림 보내기"** 버튼을 둡니다. 파일럿 시작 때 모든 인력의 기기에서 실제로 알림이 오는지 확인하는 용도입니다.

### 2. DB (마이그레이션 1개)
- `push_subscriptions`: 한 사람이 여러 기기를 가질 수 있습니다.
  - `id`, `worker_id`, `endpoint`(unique), `p256dh`, `auth`, `user_agent`, `created_at`, `last_success_at`
  - RLS: 본인 것만 추가·삭제
- `alerts`
  - `id`, `sender_id`, `agency_id`, `level`(urgent/request/info), `kind`(welfare_check/substitute/disaster/follow_up/missing_record), `client_id`(nullable), `flag_id`(nullable), `message`, `created_at`
- `alert_recipients`
  - `alert_id`, `worker_id`, `sent_count`, `response`(null/accepted/declined/acknowledged), `responded_at`
  - 응답 규칙: ②는 먼저 수락한 1명만 `accepted`로 남기고, 그 뒤 수락하려는 사람에게는 "이미 배정됨"을 보여 줍니다.
- RLS
  - 현장인력: 자기가 받은 알림만 조회하고, 자기 응답만 수정합니다.
  - 관리자: 자기 기관에서 보낸 알림과 응답 현황을 조회합니다.

### 3. 발송 (서버)
- 라이브러리: `web-push` (VAPID 방식)
  - 환경변수: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (`.env.example`에 추가)
- `POST /api/alerts`: 관리자만 호출할 수 있습니다.
  1. 받는 사람을 고릅니다.
  2. `alerts`와 `alert_recipients`를 저장합니다.
  3. 각 기기로 푸시를 보냅니다.
  - 기기 구독 정보는 다른 사람이 읽을 수 없으므로(RLS), 서버에서만 service role로 읽습니다.
- 푸시 서비스가 404/410을 돌려주면 그 구독은 만료된 것이므로 삭제합니다.
- 푸시 내용(payload)에는 알림 id와 개인정보 없는 문구만 넣습니다. 이 규칙은 테스트로 확인합니다.

### 4. 받는 사람 고르기
- 1차 범위: **관리자와 같은 기관 소속 현장인력에게만** 보냅니다. 기관 경계를 넘는 발송은 기관 협의가 필요하므로 뒤로 미룹니다.
- 받는 사람 선택 방식
  - 개인 지정: 관리자가 인력을 직접 고릅니다.
  - 대상자 담당: 그 대상자의 최근 방문 기록이 있는 같은 기관 인력 (①④)
  - 기관 전체: 같은 기관 현장인력 모두 (②)
  - 동 단위: 그 동의 대상자를 맡은 같은 기관 인력 (③)

### 5. 화면
- 관리자
  - "요청 보내기" 화면: 등급, 종류, 받는 사람, 문구 입력
  - 보낸 알림 목록: 수락·확인·미확인 현황, "전화 연락 필요" 표시
  - 이상징후 상세 화면(`/signals/[clientId]`)에 "담당 인력에게 후속 조치 요청" 버튼 (④)
- 현장인력
  - `/alerts/[id]`: 요청 내용, [수락]/[불가] 또는 [확인] 버튼
  - 하단 탭에 받은 알림 수를 표시합니다.

## 단계별 작업
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1. 기반 | 서비스 워커, 구독 저장, "알림 받기"·"테스트 알림" 버튼, VAPID 설정 | 안드로이드와 아이폰(홈 화면 앱)에서 테스트 알림 수신 |
| 2. 긴급 요청 | ①② 발송 화면, `/alerts/[id]` 응답, 먼저 수락한 사람 배정, 미확인 표시 | 관리자가 보낸 요청에 현장에서 수락하고, 관리자 화면에 반영 |
| 3. 업무 요청 | ③ 동 단위 일괄 발송, ④ 신호 화면의 후속 조치 버튼 | 확인 현황 집계 |
| 4. 자동 안내 | ⑤ 기록 누락 알림 (기존 Vercel cron 활용, 하루 1회) | 기록 없는 방문에 대해 저녁에 알림 1회 |

- 테스트는 순수 함수 위주로 작성합니다.
  - 받는 사람 선택
  - 푸시 내용에 개인정보가 없는지
  - 미확인 판정(10분 경과)
  - 먼저 수락한 사람 배정
  - 만료 구독 정리
- 아이폰은 실제 기기로 확인해야 합니다. 시뮬레이터나 데스크톱으로는 홈 화면 앱의 푸시를 검증할 수 없습니다.

## 기관에 확인할 것
1. 실제로 쓰려는 시나리오가 ①~⑤ 중 어느 것인지, 그리고 위에 없는 상황이 있는지
2. 현장인력 기기 현황: 아이폰 비율, iOS 16.4 이상인지
3. 다른 기관 인력에게도 보내야 하는지 (예: 동 행정복지센터 → 제공기관 인력). 필요하면 기관 간 권한 협의가 필요합니다.
4. 긴급 요청의 미확인 기준 시간 (기본 10분)
5. 근무시간 외(야간·주말) 발송 여부와, 그 시간에 응답할 책임이 누구에게 있는지
6. 수락하지 않은 사람에게 이어서 전화나 문자를 할 담당자가 정해져 있는지
