## 설계 결정
- **권한 판단은 DB(RLS)가 한다.** 화면 분기(proxy)는 편의일 뿐 보안 장치가 아니다.
  - `private` 스키마(외부 API에 노출 안 됨)에 `security definer` 함수 3개: `my_agency_id()`, `my_role()`, `can_see_client(client)`
  - 대상자는 `client_agencies`로 내 기관과 연결돼 있을 때만 보인다. 관리자·현장 인력 모두 같은 규칙(인수인계 목적)
  - 쓰기는 본인 기록만. 플래그 상태 변경은 관리자만. 삭제 정책은 없음(관리 스크립트로만)
  - `anon`(비로그인)은 public 테이블 권한을 모두 회수
- **계정은 관리자가 만든다** (공개 가입 끔)
  - 시드 스크립트가 `auth.users` 생성(이메일 확인 처리), `app_metadata`에 `role`·`agency_id` 기록, `workers` 행 생성
  - `app_metadata`는 비밀 키로만 바꿀 수 있어 화면 분기에 써도 위조되지 않음
- **화면 분기는 `src/proxy.ts`**: 매 요청마다 세션을 갱신하고, `getClaims()`의 `app_metadata.role`로 판단한다.
  - 판단은 순수 함수 `decideRoute(pathname, role)`로 분리하고 TDD로 만든다.
  - 비로그인 → `/login`. 로그인 상태에서 `/`나 `/login` → 역할 홈.
  - 현장 인력이 관리자 화면에 가면 `/visits`로, 관리자가 현장 화면에 가면 `/signals`로 보낸다.
  - `/api/*`는 proxy가 돌려보내지 않고, 핸들러가 직접 401을 준다.
- **Cache Components 규칙**: 세션을 읽는 부분(사용자 이름 표시)은 `<Suspense>` 안 컴포넌트에서만 읽는다(`authentication-with-cache-components.md`). 화면 내용은 아직 예시 데이터(7단계에서 교체).
- `/api/transcribe`: 로그인 필수(401)를 추가하고 같은 사이트 검사는 유지한다.
- 시험 데이터
  - 기관 2곳: A=화정1동 행정복지센터(동센터), B=서구 노인맞춤돌봄 수행기관(수행기관)
  - 계정 3개: A 관리자, A 현장, B 현장
  - 대상자 3명: C-0012=A·B 공유, C-0047=A만, C-0063=B만
  - 이메일은 `@dolbomieum.kr`(메일 발송 없음), 비밀번호는 무작위로 만들어 `.env.local`에 저장
- RLS 검증 `npm run test:rls`: 실제 프로젝트에 각 계정으로 로그인해 보이는 대상자를 확인한다. 네트워크가 필요해 `npm test`와 분리한다.
  - A 현장 = {C-0012, C-0047}
  - B 현장 = {C-0012, C-0063}
  - 비로그인 = {}
  - A 현장은 다른 기관 직원 목록을 볼 수 없다.
