# 대상자 관리 화면 (동 담당자용) 실행 계획

## Context
- **문제**
  - 지금은 앱 안에서 누구도 대상자를 추가·수정할 수 없다. DB 권한상 `clients`·`client_agencies`는 읽기만 열려 있다.
  - 대상자는 관리 명령(`npm run pilot:accounts`)으로만 넣는다.
- **사용자 요구**
  - 동 담당자가 앱에서 대상자를 등록하고, 식별번호를 **기록이 있어도** 고칠 수 있어야 한다.
  - 나머지는 추천안을 따른다.
    - 등록은 동 담당자만 한다. 번호는 자동으로 붙이고 직접 고칠 수도 있다.
    - 연령대·동, 함께 돌볼 기관은 언제든 바꾼다.
    - 종결은 숨김 처리하고 기록은 남긴다.
    - 성명 칸은 없다.
    - 다른 기관 관리자는 보기만 한다.
- **결과물**
  - 관리자 메뉴의 "대상자 목록"(지금은 '준비 중')을 실제 화면 `/clients`로 바꾼다.
  - 등록·수정·종결은 DB 함수가 권한을 판단한다.
- 범위 밖: 이름 별칭 표시(별도 결정 대기), 관리자 모바일 메뉴(기존에 없음).

## 제가 정한 기술 결정
1. **쓰기는 DB 함수(RPC, security definer)로만 한다.**
   - 대상자 생성과 기관 연결을 한 트랜잭션으로 처리하고, 권한 판단을 서버(DB)에 둔다.
   - 테이블에 insert·update 정책은 열지 않는다.
2. **"동 담당자"의 정의**
   - 역할이 `manager`이고 소속 기관 종류가 `dong_center`인 사람이다.
   - 수정·종결은 그 기관이 대상자에 연결돼 있을 때만 할 수 있다.
3. **식별번호 변경 이력 표 `client_code_history`를 두고, 한 번 쓴 번호는 다른 대상자에게 다시 주지 않는다.**
   - 이유: 기관 종이 대응표, 이미 복사해 간 글, 저장된 구술에 옛 번호가 남는다.
   - 이력이 있으면 옛 번호로 누구인지 찾을 수 있다.
4. **옛 번호로 저장해도 기록을 잃지 않는다.**
   - 기록 화면을 열어 둔 사이 번호가 바뀌면, 저장(`saveRecord`)이 이력에서 대상자를 찾아 저장한다.
5. **종결 처리**
   - `clients.closed_at`에 시각을 넣는 방식이다.
   - 현장 '오늘의 방문'·기록 화면, 이상징후 현황, 브리핑 목록, 사이드바 숫자에서 뺀다.
   - 상세 화면과 기록은 그대로 둔다. 다시 진행으로 되돌릴 수 있다.
6. **기관 목록은 함수로 조회한다.**
   - "함께 돌볼 기관" 목록은 `list_agencies()` 함수로 이름·종류만 준다.
   - 정책을 넓히지 않는 이유: 넓히면 사이드바 "연계 기관" 숫자의 뜻이 바뀐다.
7. **관리 화면 저장은 기존 관리자 화면과 같은 서버 액션 + `refresh()`로 한다.**
   - 입력이 짧은 폼이라, 배포 직후 실패해도 다시 열어 입력하면 된다.
   - 현장 기록 저장(`/api/records`)과는 사정이 다르다.
8. **`pilot:accounts` 스크립트는 대상자를 "새 번호만 추가"로 바꾼다.**
   - 지금은 덮어쓰기라, 앱에서 고친 연령대·기관과 바뀐 번호를 되돌리거나 옛 번호를 새로 만든다.

## 작업

### 1. DB 마이그레이션 `web/supabase/migrations/20261011210000_client_management.sql`
- `clients`
  - `closed_at timestamptz` 컬럼을 추가한다.
  - `check (code ~ '^C-[0-9]{4}$')` 제약을 넣는다. 기존 데이터는 모두 이 형식이다.
- `client_code_history` 표
  - 컬럼: id, client_id(→clients, cascade), old_code, new_code, changed_by(→workers, set null), changed_at
  - 인덱스: old_code, client_id
  - RLS: select는 `private.can_see_client(client_id)`, 쓰기 정책은 없다.
- private 함수
  - `private.is_dong_manager()`: 본인이 manager이고 소속 기관이 dong_center인지
  - `private.code_taken(p_code, p_client)`: 다른 대상자가 지금 쓰거나 예전에 쓴 번호인지. 같은 대상자의 옛 번호로 되돌리는 것은 허용한다.
- public 함수 (security definer, `search_path=''`)
  - 공통: anon·public 실행권은 회수하고 authenticated에만 부여한다.
  - 오류는 아래 코드로 낸다. 액션이 이 코드를 문구로 바꾼다.
    - `42501`: 권한 없음
    - `23505`: 번호 중복
    - `22023`: 입력 오류
  - `register_client(p_code, p_age_band, p_dong, p_partner_ids uuid[]) → text(code)`
    - 동 담당자만 부를 수 있다. 동은 앞뒤 공백을 빼고 2~40자여야 한다.
    - 번호가 비어 있으면 현재 번호와 이력 번호 중 가장 큰 숫자 + 1로 붙인다.
    - 대상자를 넣고, 내 기관과 함께 돌볼 기관을 중복 없이 연결한다.
  - `update_client(p_client_id, p_code, p_age_band, p_dong, p_partner_ids)`
    - 권한: 동 담당자이면서 그 대상자를 볼 수 있어야 한다.
    - 대상자 행을 `for update`로 잠근다.
    - 번호가 바뀌면 중복을 검사하고 이력에 넣는다.
    - 연령대·동을 수정한다.
    - 기관 연결은 내 기관을 빼고 동기화한다(빠진 것 삭제, 새것 추가).
  - `set_client_closed(p_client_id, p_closed boolean)`: 권한은 위와 같다. `closed_at`을 now 또는 null로 바꾼다.
  - `list_agencies() → table(id, name, type)`: 관리자만 부를 수 있다. 종류·이름 순으로 정렬한다.
- 적용과 타입 생성
  - `npx supabase db push`로 적용한다. 비밀번호는 env로 넘기고 화면에 찍지 않는다.
  - `npx supabase gen types typescript --linked --schema public > src/lib/supabase/types.ts`

### 2. 권한 검사 먼저 `web/scripts/check-rls.mts` (실패 확인 → 마이그레이션 → 통과)
- 시험 계정
  - 관리자 A = 화정1동(동 센터)
  - 현장 B = 수행기관
  - 수행기관 관리자는 임시로 만들고(비밀 키로 계정·workers 행 생성), 검사가 끝나면 지운다.
- 등록
  - 관리자 A가 번호 없이 등록하면 자동 번호가 붙고 A 기관과 연결된다.
  - 현장 B, 수행기관 관리자, 비로그인은 등록이 거부된다(42501 또는 오류).
- 수정
  - 관리자 A가 자기 대상자 번호를 바꾸면 이력 1건이 생긴다.
  - 그 옛 번호로 새 대상자를 등록하면 거부된다(23505).
  - 관리자 A가 다른 기관 대상자(C-0063)를 수정하면 거부된다.
- 종결: 관리자 A만 할 수 있다.
- 기존 경로 차단: 관리자 A가 `clients`를 직접 insert·update하면 여전히 거부된다.
- 정리: 검사에서 만든 대상자는 비밀 키로 지운다(연결·이력은 cascade).

### 3. 스키마 `web/src/schemas/client.ts` (+ `src/schemas/pilot.ts` 재사용)
- 공통 필드: `ClientCodeSchema`(C-숫자4자리), `AgeBandSchema`(50~100, 10 단위, null 허용), `DongSchema`(trim, 2~40)
  - `pilot.ts`의 ClientSchema도 이 필드를 쓰게 바꾼다(중복 제거).
- 입력 스키마
  - `ClientRegisterSchema` {code: 빈 문자열 허용, ageBand, dong, partnerAgencyIds: uuid[]}
  - `ClientUpdateSchema` {clientId: uuid, code, ageBand, dong, partnerAgencyIds}
  - `ClientClosedSchema` {clientId, closed: boolean}
  - 모두 `z.strictObject`라 다른 칸(성명 등)은 거부한다.
- 테스트: `tests/clients/schema.test.ts`

### 4. 데이터·액션 `web/src/lib/clients/`
- `data.ts`: 세션을 읽으므로 `connection()`을 쓰고 Suspense 안에서만 부른다.
  - `getClientList(includeClosed)`
    - 내 정보(역할, 기관명·종류)와 `canEdit`(동 담당자)
    - 대상자별 번호·연령대·동·종결 여부·연결 기관 이름·기록 수·마지막 방문
    - 기록은 `lib/metrics/rows.ts`의 `readAll`로 끝까지 읽는다.
  - `getClientEdit(clientId)`: 위 정보에 번호 변경 이력과 `list_agencies()` 결과를 더한다.
  - `getAgencyOptions()`: 등록 화면용
- `actions.ts` ("use server")
  - `registerClient`, `updateClient`, `setClientClosed`: Zod 검사 → `supabase.rpc(...)` → 오류 코드를 한국어 문구로 바꾼다.
  - 로그에는 오류 코드만 남긴다.
  - 성공하면 `refresh()`, 등록은 붙은 번호를 돌려준다.
- 테스트: `tests/clients/actions.test.ts`. supabase rpc를 mock해 오류 코드별 문구, 입력 거부, 성공 결과를 확인한다(`tests/dashboard/actions.test.ts` 패턴).

## 검증
1. `npm run typecheck && npm run lint && npm test`, `npm run build`
2. `npm run test:rls`: 기존 18개와 새 검사가 모두 통과해야 한다.
3. 로컬 e2e(헤드리스 크롬, 시험 계정)
   1. 관리자 A가 등록한다(자동 번호) → 현장 A의 '오늘의 방문'에 나온다.
   2. 관리자 A가 그 번호를 바꾼다 → 현장 A 목록에 새 번호가 보이고, 상세에 이력 1건이 남는다.
   3. 옛 번호를 연 기록 화면에서 저장해도 성공한다.
   4. 종결한다 → 현장 목록·현황·브리핑 목록에서 빠지고, [다시 진행]으로 돌아온다.
   5. 현장 계정으로 `/clients`에 가면 `/visits`로 돌아간다.
4. 점검으로 만든 대상자·기록은 비밀 키로 지운다. 파일럿 대상자(C-2001~2020)는 건드리지 않는다.
5. 커밋·푸시는 사용자 요청 시에만 한다. 그 뒤 운영 배포가 Ready인지 보고, 동 담당자(pilot01) 화면을 확인한다.

예상 작업량: 2~3시간, 추가 비용 없음(AI 호출 없음).
